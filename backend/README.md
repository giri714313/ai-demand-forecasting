# AI Demand Forecasting — Backend

FastAPI + SQLAlchemy backend for a multi-store retail demand forecasting engine.
Tested end-to-end against the real synthetic dataset (20 stores x 100 SKUs x 365 days,
730K sales rows, 730K inventory rows) — full run: ingest -> train -> backtest ->
forecast -> risk/recommendations, all via HTTP.

## Setup

```bash
pip install -r requirements.txt
```

## Run

```bash
uvicorn app.main:app --reload --port 8000
```

Open `http://localhost:8000/docs` for interactive Swagger docs (auto-generated by FastAPI).

## Database

Defaults to a local SQLite file (`demand_forecasting.db`) — zero setup needed.

To point at Postgres/Supabase instead (recommended once you're working with a real
retailer's data), set an environment variable before starting the server:

```bash
export DATABASE_URL="postgresql://user:pass@host:5432/demand_forecasting"
uvicorn app.main:app --reload --port 8000
```

No code changes needed — SQLAlchemy handles both.

## Workflow

1. **Ingest data** — POST CSVs to `/ingest/stores`, `/ingest/products`, `/ingest/sales`,
   `/ingest/inventory`. Expects the same column schema as the synthetic dataset
   (`stores.csv`, `products.csv`, `sales.csv`, `inventory.csv`).
2. **Train** — `POST /pipeline/train` runs feature engineering, computes baselines
   (seasonal naive, 28-day moving average), trains LightGBM, and backtests all three
   on a held-out time window (default: last 30 days). Saves the model artifact to
   `model_artifacts/lgb_demand_model.txt`.
3. **Generate forecasts** — `POST /pipeline/generate-forecasts` produces a 90-day
   recursive forecast for every store-SKU series, then derives stockout risk,
   overstock flags, replenishment quantities, and transfer recommendations.
4. **Query** — read results via `/forecasts`, `/risk/stockout`, `/risk/overstock`,
   `/recommendations/replenishment`, `/recommendations/transfers`,
   `/metrics/backtest`, `/dashboard/summary`.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/ingest/{stores\|products\|sales\|inventory}` | Upload a CSV |
| DELETE | `/ingest/reset` | Wipe all data (for swapping in a new retailer's dataset) |
| POST | `/pipeline/train` | Train + backtest |
| POST | `/pipeline/generate-forecasts` | Generate forecasts + risk + recommendations |
| GET | `/forecasts` | Forecasts, filterable by store_id/sku_id |
| GET | `/risk/stockout` | Stockout risk, filterable by level (HIGH/MEDIUM/LOW) |
| GET | `/risk/overstock` | Overstocked SKUs |
| GET | `/recommendations/replenishment` | Replenishment quantities |
| GET | `/recommendations/transfers` | Store-to-store transfer suggestions |
| GET | `/metrics/backtest` | Model comparison table (MAE/RMSE/WAPE/bias) |
| GET | `/dashboard/summary` | Executive overview aggregates |

## Testing

`test_e2e.py` is a full smoke test — ingests the real dataset, trains, generates
forecasts, and hits every endpoint. Run it directly (no server process needed,
uses FastAPI's TestClient):

```bash
python3 test_e2e.py
```

Already run once against the real data — results matched the standalone script
pipeline exactly (13.0% WAPE for LightGBM vs 14.8%/18.2% for the baselines).

## Architecture notes

- **Model engine is decoupled from the API layer** (`app/ml_engine.py`) — per the
  original plan, this lets the same forecasting engine serve Vijetha, Ratnadeep,
  or any other retailer without rewriting the web layer. Only the ingested data
  changes.
- **Forecast generation is vectorized**, not looped per-series — all 2,000 store-SKU
  series are batched together for each of the 90 forecast days, so it's ~90 model
  calls instead of 180,000.
- **This is a single-tenant schema right now.** If you're going to pitch multiple
  retailers (Vijetha, then Ratnadeep, then SuperK) against the same running service,
  the tables need a `retailer_id` column added before that — currently ingesting a
  second retailer's data would need `/ingest/reset` first. Flag this if/when it
  becomes relevant.
- **No auth yet.** Fine for local dev; needs an API key or OAuth layer before this
  is exposed anywhere a retailer could reach it.
